# Historic reference price: implementation plan

Status: implementation in progress locally, 3 October 2026. The Slice 1 migration has not been applied to production.

This plan implements the [historic reference price design](HISTORIC-REFERENCE-PRICE-DESIGN-REVIEW-2026-10-02.md). That document owns the price meaning, source precedence and evidence counts. This plan records the work order and release checks. The reference is one in-bond GBP price per 75 cl bottle and `parent_sku`; all 75 cl case sizes use it. Other bottle volumes do not receive a reference comparison.

## Slice 1: reference data contract

One new, backward-compatible migration adds the price contract while old readers continue to work. Before writing the backfill, recheck that the live owner rows are still four distinct 6 × 75 cl, in-bond wines and that no offer confirmations have appeared since the design review. Stop and revise the mapping if that baseline has changed.

1. Create an owner-only `historic_reference_candidate_view` over accepted 75 cl BBR observations, valid linked in-bond offers and linked, positive 75 cl CellarTracker records. Keep source rows authoritative. Convert case pence to whole pence per bottle with numeric division before rounding. Expose original amount and case size, source identity for detail navigation, and the correct date meaning. Exclude invalid, unlinked, excluded, zero and wrong tax-basis evidence.
2. Create `reference_price_decisions` with one positive in-bond `price_per_75cl_p INT` per `parent_sku`, optional date and note, and decision time. Add owner-only read and write permissions plus set/clear actions. The decision stores a value, not a source-row pointer. Do not infer that equal BBR and CellarTracker prices are independent confirmation.
3. Migrate the four `owner_release_anchors` rows to four wine-level decisions, dividing their 6 × 75 cl case prices by six. Preserve their notes and dates; do not call a legacy `offer_date` a proven offer date. The owner must avoid editing old release prices after this copy. Leave the old table and resolver available until the app has moved.
4. Create `resolved_reference_price_view` with at most one row per wine. Apply owner, earliest BBR observation, CellarTracker, then earliest dated offer precedence, with the documented lower-price tie-break. A candidate supports the selected value within 1p; a source price range over 1p is competing evidence. Derive `automatic, review` from changing BBR prices or CellarTracker more than 1p from the selected BBR price. Return the selected amount, status, evidence range, source and date meaning. Do not name it `release` or `initial`.

Focused database fixtures must cover Poujeaux (£210 for 12 × 75 cl, £17.50 per bottle), a 6-bottle source compared with a 12-bottle listing, all four migrated owner values, the 1p rule, an offer conflict, the two changing BBR histories, a CellarTracker correction, exclusion or relink, and clearing an owner value. Assert that anon and a non-owner authenticated identity cannot read the private views or table or call the write actions. Assert that `catalogue_view` and `catalogue_mv` contain no private price. Use the existing pgTAP suites for anchors, offers and wine cards as regression checks, then regenerate `apps/web/src/lib/database.types.ts` from the local schema. On the restricted local extract, run the new resolver for 50 Parent IDs representing two catalogue pages as the authenticated owner. Compare its `EXPLAIN (ANALYZE, BUFFERS)` plan shape and buffer counts with the current `resolved_release_anchor_view` read for those same IDs. Fix an excessive evidence scan before the Slice 2 app deploy; local elapsed time is not a production latency result.

The scenario read path is a market-only `wine_scenario_mv` plus an owner-only live join to `resolved_reference_price_view`. The reference remains live, so an owner value, accepted BBR observation, CellarTracker link or accepted offer becomes visible without waiting for a cache refresh. Prototype that join on the local extract and compare its plan with the current resolver before Slice 1 is deployed. If the plan is unacceptable, stop and revise the scenario path before deployment. The Phase 8 build can follow in Slice 3. Prepare and test the consumer slices locally before scheduling the sequential production cutover, so the edit pause begins only when deployment is ready.

The 3 October local performance check used a restricted extract of 718 BBR observations, 1,589 accepted linked offer prices and 155 linked priced CellarTracker rows. The extract held only price, date, format and Parent ID projections. These were loaded through the actual local source tables and views. A synthetic market set matched the live catalogue size of 69,901 format rows and 51,067 wines. All 2,462 extracted candidate prices matched the reconstructed candidate view in both directions. The revised resolver selected 1,471 wines, including Poujeaux at 1,750p per bottle from the 1 February 2020 BBR observation.

`EXPLAIN (ANALYZE, BUFFERS)` on 50 evidence-bearing Parent IDs gave 134 ms and 3,498 shared buffer hits for the current `resolved_release_anchor_view`, against 16 ms and 16,826 hits for the revised reference resolver. A separate 50-Parent-ID catalogue page query took 23 ms and 16,826 hits. The scenario prototype joined the resolver to all 69,901 synthetic market rows, sorted by reference and returned 50 rows in 46 ms with 17,199 hits. The candidate set was built once in each new plan; the source views and support aggregate each ran once. The first resolver shape took about 350 ms because poor source-view row estimates induced repeated candidate scans; the migration now uses one ordered choice and a grouped support check. These are local warm-cache measurements. The synthetic market rows and omission of unrelated source rows mean they cannot predict free-tier production latency. The full-catalogue candidate build remains a known per-read cost; the observed work is acceptable for the current single-owner catalogue and scenario pages, subject to production smoke checks. The restricted extract and its local validation schema were removed after this check.

Release this migration separately. Run the local migration replay, `supabase db lint --local --schema public --level warning --fail-on error` and `supabase test db`. Preview with `supabase db push --linked --dry-run`, apply only the intended migration with `supabase db push --linked`, and verify its remote entry with `supabase migration list --linked`. After an ambiguous failure, inspect server-side state before any retry. Smoke-test owner and non-owner access and the Poujeaux resolver before starting the next database migration.

## Slice 2: catalogue and wine card

Before the app cutover, compare the full current `owner_release_anchors` set, transformed to per-bottle prices with its notes and dates, against `reference_price_decisions` in both directions. `max(decided_at)` alone is insufficient because clearing an older row may leave it unchanged. If any row was added, edited or removed, reconcile the new decision table to the current owner intent and repeat the comparison. Do not deploy Slice 2 with divergent owner values. Agree a short edit pause with the owner through Slice 3; if that pause is unacceptable, combine the consumer cutovers instead of maintaining two writable price models.

1. Change `apps/web/src/lib/query/fetchCatalogue.ts` to fetch the wine-level resolver once for the Parent IDs on the current page and scale its per-bottle amount by each 75 cl row's case size. Keep the public catalogue read and its selected column list intact. Show the selected source, date meaning and competing-price indication. A failed private enrichment read must not remove public catalogue rows; it must not display a stale release number as the new reference.
2. Use a bounded owner-only read of the new resolver on the wine page, as the catalogue browser does. This avoids changing `wine_card_format_view` in this slice. Use the same case-size calculation for each 75 cl format and show evidence history. An owner-set value that loses matching evidence remains visible with `no current corroboration`. Do not enable the new value edit/clear UI yet: scenarios and Favourites still read the old resolver until Slice 3.
3. Keep `/release-prices` as a source-specific offer review screen, but remove its old owner price set/clear forms and stop calling `set_owner_release_anchor` and `clear_owner_release_anchor` from `apps/web/src/app/(protected)/release-prices/[parentSku]/[formatCode]/actions.ts`. Keep offer evidence and its correction controls. Change the old screen's navigation and comparison wording so it does not claim that an accepted offer is the unified or original release price. Rename the source-specific `Release info` panel in `apps/web/src/components/matching/MatchGroupList.tsx` and its matching-page label. Search remaining visible `Release`, `Ask vs release` and `recoup bid` labels; assign each to this slice or Slice 3 before deployment.

Decide whether 75 cl is the default visible bottle-volume filter for the catalogue before changing its filters. If selected, apply it in the database query before count, sort and pagination. Keep other volumes in source and catalogue data. The wine card may still show their market rows without reference comparisons.

Check a catalogue page, Poujeaux's wine card, and a wine with 6- and 12-bottle listings. Confirm that neither old nor new owner price edit forms are active in the interim app. Ensure reference values do not appear beside non-75 cl formats. Run focused web tests, lint and build. Slice 1's database contract must already be live and verified before this Vercel app deploy. Smoke-test the signed-in catalogue and wine card after the app deploy. During this slice, scenarios and Favourites still show their labelled legacy release comparisons; they are moved together in Slice 3.

## Slice 3: scenarios and Favourites

Use the scenario read-path decision recorded before Slice 1 deployment. Phase 8's draft `wine_scenario_mv` must not copy private owner prices into a view granted to every authenticated user or rely on the daily sweep for owner edits. Decide separately whether the scenario screen should default to 75 cl rows; apply any selected filter before scenario range queries and pagination.

1. Use the agreed scenario read path. Replace release metrics with reference metrics in `wine_scenario_view`, its registry, parser, evaluator, editor and `apps/web/src/components/scenarios/ScenarioMatches.tsx` result display. Keep the owner-only boundary through the final read surface. If a materialisation is used, prove that owner decisions and accepted BBR, CellarTracker or offer imports become visible at the documented refresh point. Enable wine-level owner value edit/clear on the reference detail only with this consumer cutover, and verify its change appears on catalogue, wine card, scenarios and Favourites.
2. Before changing stored definitions, record each scenario's current definition, result count and a bounded sample. Preview the two definitions that use release fields under the reference rule and show the differences to the owner. The owner then opens each one in the editor, replaces its affected field with the reference field, uses `Run` to preview, and chooses `Save and run` to store it. If the displayed definition differs from the one reviewed, repeat the preview. Keep legacy release fields readable and evaluable during this cutover: `parseScenarioDefinition` currently drops fields removed from its registry, so removing them early could silently strip a saved filter. Verify both saved JSON definitions and result sets after saving. Remove legacy field names from the registry in the later cleanup release and from the database view in its cleanup migration, after both conversions are confirmed.
3. Keep one Favourites row per wine. For the small favourites set (22 at design review), make a bounded owner-page read of `catalogue_mv` for those Parent IDs, restricted to `bottle_volume_ml = 750` and positive case size. Reuse the existing `catalogue_mv.ask` lowest-ask and `catalogue_mv.highest_bid_p` highest-bid values, dividing each eligible case price by case size and rounding to pence per bottle. Take the minimum ask and maximum bid per wine, preserving the current null handling; do not change `wine_market_summary_mv` for this small owner surface. Compare those prices with the same per-bottle reference. Update the `Release` and `Ask vs release` cells and any bid-recovery wording. Preserve holdings and source evidence independently of market-format filtering.

Use targeted database fixtures for 75 cl-only market aggregation, scenario filtering and sorting, null references, competing evidence and source access. Run the web scenario and Favourites tests, lint and build. Deploy each required compatible database migration and confirm the remote ledger before the matching app code. Smoke-test owner set/clear, the two converted saved scenarios and all Favourites comparisons as the owner. End the edit pause only after these consumers agree. Record whether the scenario result and latency checks passed; local plan checks are not a claim of production timing.

## Completion check

- Catalogue, wine card, scenarios and Favourites use the same resolved per-bottle reference. The 2010 Château Poujeaux shows £17.50 per bottle, or £210 for its 12 × 75 cl listing, with BBR's observation date labelled correctly.
- BBR, CellarTracker, offers and owner decisions remain inspectable. The design review found 13 purchase-evidence review wines; recount them at completion and verify that each current case is flagged. Ordinary offer disagreements retain an automatic number and show the competing range.
- No private price is readable through `anon`, a non-owner authenticated account, `catalogue_view`, `catalogue_mv` or an unrestricted materialised view.
- The saved-scenario conversion was previewed and accepted. All four owner entries survive migration. Current 75 cl Favourites ask and bid figures exclude large-format premiums.
- Database migrations and app deployments are confirmed separately. At Slice 3 go-live, record a tracked cleanup follow-up for three days of clean production operation later. It removes unused comparison columns and resolver paths, `owner_release_anchors`, and its `set_owner_release_anchor` and `clear_owner_release_anchor` functions. Check dependencies and drop with `RESTRICT`, not `CASCADE`; retain source-specific offer and BBR evidence.

The plan adds no background adjudication service, source-row pointer or new persistent evidence copy. It does not implement the optional removal of other bottle volumes from the app.
